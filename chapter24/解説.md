# Why Not Specialize Function Templates

[Why Not Specialize Function Templates?](http://www.gotw.ca/publications/mill17.htm)

<details>

```
Nontemplate functions are first-class citizens. A plain old nontemplate function that matches the parameter types as well as any function template will be selected over an otherwise-just-as-good function template.

If there are no first-class citizens to choose from that are at least as good, then function base templates as the second-class citizens get consulted next. Which function base template gets selected depends on which matches best and is the "most specialized" (important note: this use of "specialized" oddly enough has nothing to do with template specializations; it's just an unfortunate colloquialism) according to a set of fairly arcane rules:

If it's clear that there's one "most specialized" function base template, that one gets used. If that base template happens to be specialized for the types being used, the specialization will get used, otherwise the base template instantiated with the correct types will be used.

Else if there's a tie for the "most specialized" function base template, the call is ambiguous because the compiler can't decide which is a better match. The programmer will have to do something to qualify the call and say which one is wanted.

Else if there's no function base template that can be made to match, the call is bad and the programmer will have to fix the code.
```

</details>

<details>
It's a lot less intuitive to specialize function templates. For one thing, you can't partially specialize them -- pretty much just because the language says you can't.[2] For another thing, function template specializations don't overload. This means that any specializations you write will not affect which template gets used, which runs counter to what most people would intuitively expect. After all, if you had written a nontemplate function with the identical signature instead of a function template specialization, the nontemplate function would always be selected because it's always considered to be a better match than a template.

If you're writing a function template, prefer to write it as a single function template that should never be specialized or overloaded, and implement the function template entirely in terms of a class template. This is the proverbial level of indirection that steers you well clear of the limitations and dark corners of function templates. This way, programmers using your template will be able to partially specialize and explicitly specialize the class template to their heart's content without affecting the expected operation of the function template. This avoids both the limitation that function templates can't be partially specialized, and the sometimes surprising effect that function template specializations don't overload. Problem solved.
</details>




## omake

omake.cpp　(Example3)


以下はコードの抜粋
(c)で`void f<>(int*)`の時点で(a)が見えるが(b)が見えない

```C++
template<class T> // (a) same old base template as before 
void f( T ){
    cout<<"template<class T> void f(T)"<<endl;
}

template<>        // (c) explicit specialization, this time of (a)
void f<>(int*){
    cout<<"template<> void f<>(int*)"<<endl;
}

template<class T> // (b) a second base template, overloads (a) 
void f( T* ){
    cout<<"template<class T> void f<>(T*)"<<endl;
}
```


| 候補 |推論結果|引数との一致|
|---|---|---|
| (a)`f(T)` | `T=int*` | 完全一致 |
| (b)`f(T*)` | `T=int` | 完全一致 |


```sh
$ g++ omake.cpp -o p -std=c++17
$ ./p
template<class T> void f<>(T*)
```

- (b) T* が受け付ける型は、すべて (a) T でも受け付けられる
- (a) が受け付ける型の中には、(b) では受け付けられないもの(int など)がある


(a),(b),(c)のうち，より特殊化されたbが呼ばれる

## moral

```C++
// カスタマイズ用のクラステンプレート
template<class T>
struct FImpl {
    static void f(T) { /* 汎用版 */ }
};

// 利用者が触る窓口(これ自体は特殊化・オーバーロードしない)
template<class T>
void f(T t) { FImpl<T>::f(t); }

// カスタマイズはクラステンプレートの特殊化で行う
template<>
struct FImpl<int*> {             // 完全特殊化
    static void f(int*) { /* int* 用 */ }
};

template<class T>
struct FImpl<T*> {               // 部分特殊化もできる
    static void f(T*) { /* ポインタ全般用 */ }
};
```

なぜこれで問題が解決するのか
1. **オーバーロード解決が絡まない**
窓口の f は1つしかないので、Example 3 のように「どのベーステンプレートが選ばれるか」で迷う余地がありません。

2. **特殊化の選択ルールが素直**
クラステンプレートでは、最も特殊化された版がそのまま選ばれます。宣言順や「どのベースに属するか」で結果が変わることはありません。

3. **部分特殊化ができる**
関数テンプレートは部分特殊化できませんが、クラステンプレートならできます。上の FImpl<T*> のような書き方が可能です。

4. **使い勝手は変わらない**
窓口が関数テンプレートなので、利用者は f(p) と書くだけで引数から型が推論されます。クラステンプレートを直接使わせる場合のように、FImpl<int*>::f(p) と書かせる必要はありません。
